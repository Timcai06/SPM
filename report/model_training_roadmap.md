# 股市预测系统三阶段演进路线图

本路线图基于当前工程现状、数据库结构、任务 1 到任务 3 的完成情况，以及“从事件工程链走向数学模型训练”的真实差距整理而成。

目标不是继续泛泛讨论“能不能做模型”，而是明确：

1. 现在立刻做什么
2. 近一周做什么
3. 面向正式预测模型还需要补什么

---

## 一、当前判断

当前系统已经完成了以下关键底座：

- 任务 1：原始文本 -> 候选事件 -> 结构化事件 -> 标准事件簇
- 任务 2：事件 -> 公司关联
- 任务 3：公司关系边 -> 事件传播边
- 初步训练层：`model_event_samples`

这意味着我们已经有了“事件建模系统”，但还没有真正形成“可稳定训练的预测数据集”。

当前最核心的问题不是模型结构，而是训练数据本身仍不够：

- 样本量偏小
- 负样本缺失
- 标签稀疏
- 公司控制变量缺失
- 历史回溯能力不够强

因此，项目主线应当从“继续搭事件工程链”切换为“训练数据工程化”。

## 二、阶段 1：现在立刻做（1 到 3 天）

这一阶段的目标是：让训练表从“有结构”变成“可用”。

### 1. 稳定任务 1 主链路

目标：

- 继续在 run tree 扩库
- 固定采用中等规模批量采集
- 采集与分析彻底解耦

执行策略：

- `task1 run --skip-validate` 作为扩库主命令
- `task1 feature` 单独跑，不阻塞入库
- 所有运行结果以数据库表为准，不以 CSV 为准

### 2. 把训练样本层真正用起来

目标：

- 固定使用 `model_event_samples` 作为训练入口表
- 把事件特征、公司特征、链接强度统一到单行样本

当前状态：

- 已有 `model_event_samples`
- 但标签字段仍可能为空

立刻要做：

- 在 run tree 跑出可用的 `task1_event_return_dataset`
- 回到 main tree 重新执行 `task1 train-samples`
- 验证 `label_car_w1 / label_car_w3 / label_car_w5` 非空样本数

### 3. 修正所有“demo 时代遗留逻辑”

目标：

- 消除对历史演示样例的依赖
- 让系统默认面向真实采集数据运行

当前重点：

- `task1 check` 已改为生产口径
- 下一步继续检查是否仍有 demo/手工样例假设残留

## 三、阶段 2：近一周内做（训练底座扩容）

这一阶段的目标是：把训练表从几十条提升到几百到几千条可用样本。

### 1. 启动历史补报，而不是只等当天新闻

这是最重要的一步。

原因：

- 每天新增事件数量太少
- 仅靠实时数据无法快速积累训练样本
- 数学模型本质上学习的是历史规律，不是今天的故事

建议：

- 从过去 1 到 3 年开始回溯
- 优先补公告类、政策类、行业类高价值事件
- 先做“高质量历史补报”，不是盲目全量抓取

### 2. 引入负样本

目标：

- 不仅记录“有事件”
- 还要记录“无显著事件的普通交易日”

为什么重要：

- 如果只有正样本，模型会学成“只要看到新闻就预测有反应”
- 这会导致严重的幸存者偏差

建议做法：

- 以公司-交易日为粒度，构造一批“未触发重大事件”的负样本
- 与事件样本统一进入训练表或平行训练表

### 3. 补公司控制变量表

建议新增：

- `company_stats`

字段方向：

- 总市值
- 流通市值
- 市盈率
- 波动率
- Beta
- 近 20 日/60 日收益
- 换手率

作用：

- 这些变量是模型中极重要的控制项
- 可以降低“把公司自身风格误当成事件效应”的风险

### 4. 固定时间切分训练规则

必须明确：

- 禁止随机打乱后训练
- 必须按时间做 train / valid / test

建议：

- 训练集：过去时期
- 验证集：中间时期
- 测试集：最近时期

这一步要尽早写进项目规范，因为它决定你后续所有模型结果是否可信。

## 四、阶段 3：面向正式预测模型做（任务 3 后半段到任务 4）

这一阶段的目标是：从“结构化规则系统”升级为“多因子预测系统”。

### 1. 丰富训练特征

最终训练特征建议由三类构成：

- 事件因子
  - 事件类型
  - 热度
  - 强度
  - 影响范围
  - 预测性
  - 情绪
- 公司因子
  - 行业
  - 市值
  - 波动率
  - 动量
  - 基本面
- 图谱因子
  - 是否直接关联
  - 传播强度
  - 关系类型
  - 节点中心度
  - 上下游层级

### 2. 引入语义向量

方向正确，但不是当前第一优先。

适合在样本规模上来之后做：

- 事件摘要 embedding
- 政策全文 embedding
- 事件-公司语义匹配增强

意义：

- 比起纯规则标签，向量能表达更细微的语义差别
- 对“同属政策类但语气不同”的事件会更有帮助

### 3. 引入图模型/GNN

适合在任务 3 关系边质量提升后做。

前提：

- `event_company_links` 比较稳定
- `company_relations` 覆盖率足够
- `event_propagation_links` 有可解释性

作用：

- 不只预测直接命中的公司
- 还能学习事件沿产业链传播的衰减规律

但这一步必须排在“传统模型可用”之后。

建议顺序：

1. 先做逻辑回归 / XGBoost / LightGBM 基线
2. 再做图特征增强
3. 最后再尝试 GNN

## 五、接下来项目主线建议

接下来不要再把主要精力放在“继续微调少量规则细节”上，而应该按以下顺序推进：

1. run tree 持续扩库
2. run tree 历史补报
3. main tree 补标签稳定性
4. main tree 增加 `company_stats`
5. main tree 补负样本机制
6. 形成真正可训练的数据集
7. 再开始第一版基线模型

---

## 六、最终判断

当前系统并不是“不够好”，而是进入了新的阶段。

之前我们解决的是：

- 如何识别事件
- 如何结构化事件
- 如何关联公司
- 如何表达传播

现在真正要解决的是：

- 如何把这些结构化结果转化成大规模、可监督、可验证的训练样本

所以后续主线应当明确转为：

`事件工程 -> 训练数据工程 -> 基线模型 -> 高级模型`

这才是从赛题工程系统走向数学预测系统的正确演进路径。
