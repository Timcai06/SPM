# 本地 LLM 辅助事件判断方案

## 1. 目标

本方案的目标不是用本地大模型替代整个任务 1 规则链，而是在当前规则主导框架下，引入 `Ollama + 本地模型` 作为辅助判断层，提升下面三类质量：

- `is_event` 边界样本判断
- 四维分类稳定性
- 事件摘要与证据解释质量

当前项目最适合的定位是：

- 规则：负责稳定、低成本、可解释的第一层筛选
- 本地 LLM：负责文本理解、模糊样本辅助判断、摘要增强
- 下游结构化表：仍然只接受固定枚举和确定性字段

## 2. 当前系统已经具备的基础

当前仓库里，本地 LLM 入口已经存在于：

- [classify.py](/Users/tim/股市预测模型/src/capabilities/events/classify.py)

已具备能力：

- `--use-llm`
- `--llm-max-rows`
- 远程兼容 API 失败后回退本地 `ollama`
- 当前已接通 `qwen3:8b`
- 输出结果会写入 `classification_evidence`

说明：

- 主链路已经支持“小批量 LLM enrich”
- 当前缺的不是能力，而是**触发策略、输出 schema、融合规则**的正式化

## 3. 不推荐的接法

后续不要这样做：

1. 不要让 LLM 直接替代 `is_event` 主判断
2. 不要让 LLM 直接给最终数值型热度/强度打分
3. 不要让 LLM 直接决定最终关联公司
4. 不要让 LLM 进入标签生成层

原因：

- 会破坏可复现性
- 会污染下游枚举
- 会让训练数据口径不稳定

## 4. 推荐的接法

### 4.1 放置位置

本地 LLM 应该只接在任务 1 的**分类阶段**，即：

`采集 -> 清洗 -> 规则初判 -> 本地 LLM enrich -> 枚举归一化 -> structured_events`

而不是：

- 放在 `feature_return`
- 放在 `build_model_samples`
- 放在 `event_company_links` 末端直接改分

### 4.2 角色定义

本地 LLM 的职责只包含 4 类：

1. 边界样本判断  
   规则分数接近阈值时，帮助判断是不是“真金融事件”

2. 分类辅助  
   对下面字段给出建议：
   - `event_subject_type`
   - `industry_type`
   - `sentiment`
   - 可扩展到 `predictability_type`

3. 摘要增强  
   生成更适合建模和答辩的标准化事件摘要

4. 证据解释  
   输出一句短的解释，说明为什么判断成该类别

## 5. 推荐触发条件

不是所有文本都调用本地 LLM，只对高价值样本调用。

### 5.1 第一优先级：边界样本

触发条件：

- `event_score == event_threshold`
- 或 `event_score == event_threshold + 1`

原因：

- 这类样本最容易误判/漏判
- LLM 的文本理解价值最高

### 5.2 第二优先级：分类模糊样本

触发条件：

- `industry_type == 其他`
- 或 `event_subject_type` 命中不稳定
- 或多标签命中数接近

原因：

- 规则在这类样本上最容易“分类粗糙”

### 5.3 第三优先级：高价值来源样本

触发条件：

- 政策源
- 交易所公告
- 证监会制度类新闻
- 地缘冲突类新闻

原因：

- 这类文本对下游影响更大
- 值得用 LLM 做摘要和证据增强

### 5.4 不建议调用的样本

- 规则已明确判为非事件的纯噪声
- 明显重复文档
- 常规披露模板文本

原因：

- 浪费推理预算
- 收益极低

## 6. 推荐输出 schema

本地 LLM 不应输出自由文本，应输出固定 JSON：

```json
{
  "is_event_candidate": true,
  "event_subject_type": "政策类",
  "industry_type": "科技",
  "sentiment": "利好",
  "predictability_type": "预披露型",
  "summary": "一句标准化事件摘要",
  "reason": "一句短解释",
  "confidence": 0.78
}
```

要求：

- 所有枚举必须映射回现有合法值
- `summary` 必须是单句、短文本
- `reason` 只做解释，不进入训练特征
- `confidence` 只用于辅助，不直接替代规则

## 7. 与规则的融合方式

### 7.1 `is_event`

不直接让 LLM 覆盖规则结果，推荐方式：

- 规则先产出 `is_event_rule`
- LLM 产出 `is_event_candidate`
- 最终结果按以下逻辑：

1. 若规则明确为强非事件  
   直接保留规则结果，不调用覆盖

2. 若规则是边界事件  
   LLM 可作为二次确认

3. 若规则强事件、LLM 弱反对  
   先保留规则结果，但在证据字段里记录冲突

推荐原则：

- **规则优先，LLM 只做边界矫正**

### 7.2 四维分类

推荐方式：

- 规则先给初始类别
- LLM 给建议类别
- 若规则命中弱、LLM 置信度高，则允许覆盖
- 覆盖前必须过枚举冻结函数

推荐允许覆盖的字段：

- `event_subject_type`
- `industry_type`
- `sentiment`

暂不建议直接覆盖：

- `duration_type`
- `impact_scope`

因为这两个字段更适合继续保持规则定义。

## 8. 当前最优实现策略

基于现有代码，我建议后续按三步走。

### 第一步：把 LLM enrich 变成“严格触发”

当前 `classify.py` 已支持小批量 enrich，但还应进一步收口到：

- 只 enrich 边界样本
- 只 enrich `industry_type=其他`
- 只 enrich 高价值来源

这样可以让本地模型发挥在最值钱的位置。

### 第二步：把 `classification_evidence` 结构化

当前已经会写：

- `llm=1`
- `llm_backend=ollama`
- `llm_subject=...`
- `llm_industry=...`
- `llm_sentiment=...`

建议继续统一为两层：

- 规则证据
- LLM 证据

例如：

`rule_subject=政策类|rule_industry=其他|llm_subject=政策类|llm_industry=科技|llm_conf=0.78`

### 第三步：抽样复核

要验证本地 LLM 是否真有价值，不能只看“跑通了”，而要看：

- LLM 是否降低了 `industry_type=其他`
- LLM 是否提高了 `is_event` 边界样本准确率
- LLM 是否让摘要更稳定

## 9. 最推荐的提示词方向

提示词不应该是“自由发挥分析这条新闻”，而应该是：

1. 判断它是不是会影响市场/行业/个股的金融事件
2. 若是，按固定枚举输出类型
3. 给一句标准摘要
4. 给一句原因
5. 严禁输出枚举外的值

这比开放式提示更适合结构化生产。

## 10. 后续评估指标

是否继续扩大本地 LLM 使用范围，应该看这些指标：

1. `is_event` 边界样本人工准确率
2. `industry_type=其他` 占比是否下降
3. `classification_evidence` 可解释性是否提升
4. LLM 引入后是否导致分类抖动

如果前 3 个变好、最后 1 个可控，就继续扩大。

## 11. 建议的落地顺序

最推荐顺序：

1. 先让本地 LLM 只辅助 `classify.py`
2. 再针对边界样本做人工复核
3. 最后再考虑把 LLM 结果作为 `event_company_links` 的弱证据

不建议直接让 LLM 参与：

- 事件收益标签
- 训练样本拼接
- 最终公司排序

## 12. 当前结论

本地 LLM 的最佳角色不是替代规则，而是：

**在规则已经把大框架稳定住之后，专门解决边界理解、分类模糊和摘要质量问题。**

对你们当前系统来说，最优落点就是：

- 任务 1 分类阶段做小批量 enrich
- 只处理高价值、边界、模糊样本
- 保持规则优先、枚举冻结、证据可追溯

这样既能提升数据质量，又不会破坏你后面交付给建模同学的数据口径。
