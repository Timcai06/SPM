# 任务 3 关系图设计说明

## 1. 目标

任务 3 不直接从零开始做复杂知识图谱，而是在任务 1 的事件表、任务 2 的事件-公司直连关系之上，补出一层“公司关系边”和“事件传播边”，用于刻画事件影响如何从直接受影响公司向相关公司扩散。

当前目标不是做全市场完备图谱，而是先完成一个可解释、可复现、可答辩的一跳传播版本。

## 2. 当前图模型

当前采用两类边：

- `company_relations`
  - 表示公司与公司之间的静态关系边
  - 典型关系类型：
    - `供应链`
    - `同产业链`
    - `军工链`
    - `新能源链`
    - `AI产业链`
    - `金融链`
    - `消费出行链`

- `event_propagation_links`
  - 表示事件影响从“源公司”传播到“目标公司”的动态结果边
  - 由 `structured_events + event_company_links + company_relations` 联合生成

## 3. 设计原则

### 3.1 先做一跳，不先做多跳

一跳传播最容易解释：

`事件 -> 源公司 -> 公司关系边 -> 目标公司`

这样做的原因：

- 逻辑简单，容易答辩
- 噪声可控
- 便于人工修边
- 不会过早引入路径爆炸问题

### 3.2 关系边必须可解释

每条关系边至少保留：

- `relation_type`
- `relation_strength`
- `direction`
- `evidence`

这保证后续展示时，不是只说“模型算出来有关联”，而是能解释“为什么传播到这家公司”。

### 3.3 传播分数保持简单

当前采用：

`propagation_score = source_link_score * relation_strength`

其中：

- `source_link_score`：事件对源公司的直连得分
- `relation_strength`：公司关系边强度

优点：

- 可解释
- 易调参
- 易扩展

后续若要升级，可再加入：

- 关系类型权重
- 行业一致性权重
- 事件类型权重

## 4. 为什么现在不用 Neo4j

当前阶段不强依赖 Neo4j，原因有三点：

- 任务 1 和任务 2 的主数据还在持续清洗
- 当前关系边数量很小，用 PostgreSQL 足够
- 赛题答辩更关心“方法是否合理、链路是否打通、结果是否可解释”，不强制要求图数据库产品化

所以当前策略是：

- 先用 PostgreSQL 把图结构跑通
- 等关系边规模和类型稳定后，再决定是否迁移到 Neo4j

## 5. 当前最值得补的关系边

优先顺序如下：

1. 军工链
   - 地缘事件、军品合同事件最容易出结果
2. 新能源/储能链
   - 政策、容量电价、电网建设事件容易形成传播
3. AI/机器人链
   - 样机、芯片、数字化服务相关事件容易构成主题联动
4. 金融链
   - 券商、保险、资本平台可形成情绪联动
5. 消费出行链
   - 旅游、酒店、交通场景适合做弱传播示例

## 6. 当前版本的边界

当前版本还没有做：

- 多跳传播
- 时间衰减
- 自动抽取真实供应链
- 基于公告正文自动建边
- 人工审核工作流

因此当前版本定位是：

“任务 3 的可运行图传播底座”，不是最终图谱系统。

## 7. 下一步怎么继续

建议按这个顺序推进：

1. 扩充 `company_relations_seed.csv`
2. 做关系边人工复核
3. 按事件类型分层看传播结果
4. 再考虑二跳传播或自动抽边

当前最重要的不是把图做大，而是把边做对。
